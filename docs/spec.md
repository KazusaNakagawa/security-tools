# alertcheck 仕様書

IPA「不正アクセスによる漏えい等の事案を踏まえ、速やかに実施すべき対策等について」（2026-10-09 公表）の点検・対策項目を、自組織がどこまで満たしているか診断するローカル実行ツールの仕様を定める。

- 版: 0.1（初版ドラフト）
- 作成日: 2026-10-17
- 関連: [設計書](./design.md) / [task.md](./task.md)

## 1. 目的

IPA の注意喚起は「点検」「対策」「経営者の 3 原則」の 3 層で構成される。各項目には、HTTP 応答やログから機械的に判定できるものと、組織の運用実態を人が回答しないと判定できないものが混在している。

alertcheck は次の 2 つを 1 回の実行で行い、IPA の項目ごとに達成状況と根拠を一覧化する。

1. 自組織の公開資産・ログ・アカウント台帳・依存ライブラリに対する自動診断
2. 自動診断できない項目に対する質問票（自己評価）の集計

AeyeScan のような商用 DAST（網羅的な脆弱性診断）を置き換えるものではない。IPA 注意喚起への対応状況を短時間で棚卸しし、抜けている対策を洗い出すことを目的とする。

## 2. 利用者と利用場面

| 利用者 | 場面 | 主な出力 |
|---|---|---|
| 情報システム担当・開発者 | 注意喚起を受けた緊急点検、四半期ごとの定期点検 | 技術詳細レポート（検出内容・再現手順・修正方針） |
| セキュリティ責任者 | 対応状況の把握、未対応項目の割り振り | IPA 項目別の達成状況マトリクス |
| 経営層 | 対応状況の報告を受ける | 1 ページのサマリー（達成率・重大リスク上位） |

## 3. 前提と制約

- Docker が動く端末（macOS / Linux / Windows + WSL2）で、`docker compose` によりローカル実行する。SaaS やクラウド上の常駐サーバは使わない。
- 診断対象は自組織が管理権限を持つ資産に限る。第三者の資産を診断すると不正アクセス禁止法等に抵触するおそれがあるため、スコープ定義ファイルでの明示的な許可を必須とする（6.1 参照）。
- 既定の動作は非破壊・低負荷とする。ログイン試行やファジングなど対象に負荷や副作用を与える検査（アクティブ検査）は、明示的なオプション指定がない限り実行しない。
- 診断結果、取り込んだログ、アカウント台帳は端末内にのみ保存し、外部へ送信しない。例外は脆弱性 DB の更新（Trivy DB、OSV）と、利用者が設定したクラウド API への読み取り呼び出しのみとする。オフラインモードではこれらも行わない。
- 本ツールは IPA の公式ツールではない。判定基準は本仕様書の解釈に基づく。

## 4. 診断基準（IPA 項目との対応）

IPA 注意喚起の各項目に ID を振り、判定方法を定める。判定方法の記号は次の通り。

- **自動**: ツールが自動で判定する
- **半自動**: 利用者が提供したファイル（ログ、台帳 CSV 等）をツールが解析して判定する
- **質問**: 質問票の回答で判定する

### 4.1 速やかに実施すべき点検（P 系）

| ID | IPA の項目 | 判定方法 | 使用する検査 |
|---|---|---|---|
| P1-1 | 独自構築した外部公開アプリケーション・サービスを把握している | 自動 + 質問 | 資産台帳とスコープの突合、DNS / ポート探索で台帳外の公開サービスを検出 |
| P1-2 | 直近ログに異常がないか確認した（エラー量、平時との差異） | 半自動 | ログ解析（4xx/5xx 日次推移、ベースライン乖離、許可リスト外 URL への 200 応答、攻撃シグネチャ） |
| P1-3 | 確認期間を段階的に広げた（直近 1 か月、続いて 3 か月） | 半自動 | ログ解析の対象期間カバレッジ判定 |
| P1-4 | 未適用の脆弱性対応パッチがない | 自動 + 半自動 | バナー・ヘッダからの製品バージョン推定、ロックファイル / SBOM / コンテナイメージの脆弱性スキャン |
| P2-1 | 利用中のクラウドサービス・VPN 等を網羅的に把握している | 質問 + 半自動 | 外部サービス台帳の有無・更新日、VPN 機器等の公開ポート検出 |
| P2-2 | 外部サービスごとにログの異常を確認した | 半自動 | 認証ログ解析（失敗急増、深夜帯ログイン、未知 IP） |
| P2-3 | 異常なアカウント（不正作成、削除済みアカウントの再有効化等）がない | 半自動 | アカウント台帳監査 |
| P3-1 | 不要な情報を保有していない | 質問 + 半自動 | データ台帳の保持理由・保持期限、DB メタデータの個人情報カラム検出 |
| P3-2 | 保有する情報資産を正確に把握している | 質問 | データ台帳の有無・網羅性 |

### 4.2 外部公開アプリケーションの対策（A 系）

| ID | IPA の項目 | 判定方法 | 使用する検査 |
|---|---|---|---|
| A-1 | 外部公開範囲の見直し | 自動 | 管理画面・API ドキュメント・機微ファイルの公開検出、管理系ポート（SSH/RDP/DB 等）の公開検出、ディレクトリリスティング |
| A-2 | 認証機能の強化（多要素認証、パスワード） | 自動 + 質問 | ログインフォームの HTTPS 化、Cookie 属性、（アクティブ時）ロックアウト・パスワードポリシー試験、MFA 導入状況の回答 |
| A-3 | アカウント権限付与の見直し | 半自動 + 質問 | アプリ管理者アカウントの台帳監査 |
| A-4 | API 連携等の管理状況の見直し | 自動 + 質問 | OpenAPI / GraphQL イントロスペクションの公開、未認証で応答する API、CORS 設定、API キー棚卸しの回答 |
| A-5 | ログ取得内容・保持期間の見直し | 半自動 + 質問 | 提供ログの項目充足（日時、送信元、URL、ステータス、ユーザー）と保持期間 |
| A-6 | 追加のセキュリティ対策の検討 | 自動 + 質問 | セキュリティヘッダ、TLS 設定、エラー時のスタックトレース露出、WAF 導入の回答 |

### 4.3 外部サービスの対策（S 系）

| ID | IPA の項目 | 判定方法 | 使用する検査 |
|---|---|---|---|
| S-1 | 認証機能の強化 | 半自動 + 質問 | 台帳の MFA 列、クラウド連携時は IAM の MFA 設定 |
| S-2 | アカウント付与範囲の見直し | 半自動 | 管理者権限保有者数、共有アカウントの検出 |
| S-3 | アカウント棚卸し運用の見直し | 半自動 + 質問 | 長期未使用アカウント、退職者アカウント、棚卸し実施日 |
| S-4 | API 管理状況の確認 | 半自動 + 質問 | アクセスキー / トークンの経過日数、未使用キー |
| S-5 | ログ取得・保持期間の見直し | 半自動 + 質問 | 監査ログ有効化・保持期間（クラウド連携時は CloudTrail 等） |

### 4.4 保有データの対策（D 系）

| ID | IPA の項目 | 判定方法 | 使用する検査 |
|---|---|---|---|
| D-1 | データ保有の是非の再検討 | 質問 + 半自動 | データ台帳の保持理由・期限超過 |
| D-2 | 保管場所の再検討 | 質問 + 自動 | 公開ストレージ（クラウド連携時は S3 のパブリック設定）、Web 公開領域内のバックアップ・ダンプファイル検出 |
| D-3 | アクセスログ取得・保持期間の見直し | 質問 | DB 監査ログの有無と保持期間 |
| D-4 | データの暗号化 | 質問 + 自動 | 通信の暗号化（TLS）、クラウド連携時はストレージ暗号化設定 |

### 4.5 経営者が認識すべき 3 原則（M 系）

| ID | IPA の項目 | 判定方法 |
|---|---|---|
| M-1 | サイバーセキュリティリスクを経営課題と認識し、経営者がリーダーシップを取っている | 質問 |
| M-2 | サプライチェーン全体を含めた対策に目配りしている | 質問 |
| M-3 | 平時・緊急時に関係者と積極的にコミュニケーションを取っている | 質問 |

## 5. 判定ルール

### 5.1 検出結果（Finding）

各検査は 0 件以上の Finding を出力する。Finding は次の属性を持つ。

| 属性 | 内容 |
|---|---|
| `check_id` | 検査 ID（例 `http.headers.csp_missing`） |
| `ipa_items` | 対応する IPA 項目 ID の配列（例 `["A-6"]`） |
| `severity` | `critical` / `high` / `medium` / `low` / `info` |
| `target` | 対象（URL、ホスト:ポート、アカウント名、ファイル名など） |
| `title` / `description` | 何が問題か |
| `evidence` | 根拠（応答ヘッダ抜粋、ログ集計値、台帳の該当行など。機微情報はマスクする） |
| `remediation` | 修正方針 |
| `references` | 参考資料（IPA、OWASP、CVE 等） |

重大度の目安は次の通り。

- **critical**: 個人情報や認証情報の漏えいに直結する状態（`.env` や DB ダンプの公開、既知の悪用済み脆弱性 = CISA KEV 掲載 CVE の残存、退職者の管理者アカウントが有効）
- **high**: 侵入の足掛かりになる状態（管理系ポートのインターネット公開、CVSS 7.0 以上の未修正脆弱性、MFA なしの管理者アカウント）
- **medium**: 攻撃を容易にする設定不備（CSP 等ヘッダ欠如、スタックトレース露出、GraphQL イントロスペクション有効）
- **low**: 情報露出や運用上の弱点（サーババナーのバージョン表示、長期未使用の一般アカウント）
- **info**: 判定の補助情報（検出した技術スタック、ログ期間）

### 5.2 IPA 項目の判定（ItemResult）

各 IPA 項目について、関連する Finding と質問回答から次のいずれかを判定する。

| 判定 | 条件 |
|---|---|
| 達成 | 必要な検査をすべて実行し、medium 以上の Finding がなく、質問回答も「実施済み」 |
| 一部達成 | medium / low の Finding のみ、または質問回答が「一部実施」 |
| 未達 | high 以上の Finding がある、または質問回答が「未実施」 |
| 未確認 | 判定に必要な入力（ログ、台帳、回答）が提供されていない |
| 対象外 | 質問で「該当なし」と回答（例: 外部公開アプリを持たない） |

「未確認」を「達成」と扱わないことを原則とする。入力が足りない項目は、何を提供すれば判定できるかをレポートに明記する。

### 5.3 総合スコア

- 達成率 = 達成 ÷（判定対象項目数 − 対象外）
- 一部達成は 0.5 として加算する
- 未確認は分母に含め、加算しない（入力を揃えないとスコアが上がらないようにする）
- スコアとは別に、critical / high の Finding 件数を必ず併記する。スコアが高くても critical が 1 件あれば最上段に警告を出す

## 6. 機能要件

### 6.1 スコープ定義

- `scope.yaml` で診断対象（ドメイン、URL、IP / CIDR）、除外対象、実行許可を定義する。
- `authorization.confirmed: true` と責任者名・確認日がない場合、ネットワーク検査を一切実行しない。
- スコープ外のホストへのリダイレクトやリンクはたどらない。
- 1 ホストあたりの最大リクエストレート（既定 5 req/s）と同時接続数を設定できる。

### 6.2 自動診断（ネットワーク）

| 検査グループ | 内容 | 既定 |
|---|---|---|
| `discovery` | スコープ内ドメインの DNS 解決、サブドメイン列挙（証明書透明性ログ crt.sh・利用者提供リスト）、台帳との差分 | 有効 |
| `ports` | 主要 TCP ポート（上位 100 + 管理系ポート一覧）の公開状況とサービス識別 | 有効 |
| `tls` | 対応プロトコル（TLS 1.0/1.1 の残存）、証明書の有効期限・ホスト名一致、弱い暗号スイート | 有効 |
| `http.headers` | HSTS、CSP（`frame-ancestors` 含む）、X-Content-Type-Options、Referrer-Policy、Permissions-Policy、Server / X-Powered-By のバージョン露出 | 有効 |
| `http.cookies` | セッション Cookie の Secure / HttpOnly / SameSite | 有効 |
| `http.exposure` | 機微パス（`.git/`、`.env`、`*.bak`、`*.sql`、`phpinfo.php`、`/server-status` 等）、管理画面、ディレクトリリスティング、API ドキュメント | 有効 |
| `http.errors` | 存在しないパス・不正パラメータに対するエラー応答のスタックトレース・内部情報露出 | 有効 |
| `api` | OpenAPI / Swagger の公開、GraphQL イントロスペクション、未認証で 200 を返す API（利用者提供のエンドポイント一覧）、CORS のワイルドカード + 資格情報許可 | 有効 |
| `auth.passive` | ログインフォームの検出、HTTP での送信、autocomplete、MFA 画面の有無の推定 | 有効 |
| `auth.active` | 試験用アカウントによるロックアウト・レート制限・パスワードポリシー確認 | **無効（`--active` 指定時のみ）** |
| `vuln.version` | 検出した製品バージョンと OSV / NVD の照合、CISA KEV 掲載の判定 | 有効 |
| `vuln.templates` | Nuclei の非破壊テンプレート（`exposure`、`misconfig`、`cve` のうち safe タグ）による検査 | 有効 |

### 6.3 半自動診断（ファイル取り込み）

| 検査グループ | 入力 | 内容 |
|---|---|---|
| `logs.access` | Apache / Nginx combined、JSON Lines、AWS ALB / CloudFront ログ | 日次のリクエスト数・4xx・5xx の推移、直近 7 日と過去平均の乖離（z スコア）、許可リスト外 URL への 200 応答、SQLi / パストラバーサル / Web シェル等のシグネチャ一致、単一 IP からの集中アクセス、1 か月・3 か月の期間カバレッジ |
| `logs.auth` | 認証ログ CSV / JSON（共通スキーマにマッピング） | ログイン失敗の急増、パスワードスプレー（多アカウント × 少回数）、営業時間外ログイン、過去に出現しない IP / 国からの成功ログイン（GeoIP DB 提供時） |
| `accounts` | アカウント台帳 CSV（サービスごと）、人事名簿 CSV | 名簿にない有効アカウント（退職者・不明）、直近作成で申請記録のないアカウント、無効→有効の状態変化（前回実行との差分）、MFA 未設定、管理者権限の過多、90 日以上未使用、共有アカウントの疑い |
| `deps` | リポジトリ / ロックファイル / SBOM（CycloneDX・SPDX）/ コンテナイメージ名 | 既知脆弱性（Trivy / OSV-Scanner）、サポート終了ランタイム（PHP 7.x 等）の検出 |
| `data` | データ台帳 CSV、（任意）DB 接続情報 | 保持期限超過、保持理由の空欄、DB メタデータ（テーブル名・カラム名のみ）からの個人情報らしき列の検出。**行データは読まない** |

### 6.4 クラウド設定診断（任意）

- AWS の読み取り専用認証情報（`SecurityAudit` ポリシー相当）が渡された場合のみ実行する。
- 実装は Prowler に委譲し、結果を IPA 項目へマッピングする（例: ルートアカウントの MFA → S-1、CloudTrail の保持 → S-5、S3 パブリックアクセス → D-2、0.0.0.0/0 に開いた 22/3389 → A-1）。
- Microsoft 365 / Entra ID、Google Workspace は第 2 段階で対応する。それまでは管理画面からエクスポートした CSV を `accounts` 検査に渡す運用とする。

### 6.5 質問票

- 自動判定できない項目と、自動判定を補う項目について YAML 形式の質問票を提供する。
- 回答は「実施済み / 一部実施 / 未実施 / 該当なし」の 4 択と、任意の補足・根拠資料のパスとする。
- `alertcheck questionnaire init` で空の回答ファイルを生成する。ローカル Web UI（6.7）からも回答できる。
- 質問票の全文は設計書の付録に定義する。

### 6.6 レポート

| 形式 | 用途 |
|---|---|
| HTML（単一ファイル、外部リソース不使用） | 閲覧・共有用。経営サマリー → IPA 項目マトリクス → Finding 詳細の順に構成 |
| Markdown | チケットや社内 Wiki への転記用 |
| JSON | CI 連携・他ツール連携用（スキーマは設計書で定義） |
| CSV | Finding 一覧の表計算ソフトでの管理用 |

- 前回実行との差分（新規・解消・継続）を表示する。
- 「未確認」項目には、判定に必要な入力ファイルと取得方法を表示する。
- レポート内の認証情報・トークン・メールアドレス等はマスクする。

### 6.7 ローカル Web UI（第 2 段階）

- `alertcheck serve` で `127.0.0.1` のみに待ち受ける Web UI を起動する。
- 質問票の回答、実行履歴の閲覧、Finding の対応状況（未対応 / 対応中 / 対応済み / リスク受容）の記録を行う。
- 認証は持たないため、`127.0.0.1` 以外へのバインドは禁止する。
- 例外として、AWS 上で認証付きリバースプロキシ（ALB + OIDC）の背後に置く場合に限り、外部インターフェースへの待ち受けを許可する（設計書 14.7）。

### 6.8 CLI

```
alertcheck init                     # scope.yaml・質問票・入力ディレクトリの雛形を生成
alertcheck validate                 # 設定と入力ファイルの検証（実行前チェック）
alertcheck scan [--only GROUP...] [--skip GROUP...] [--active] [--offline]
alertcheck report [--run RUN_ID] [--format html,md,json,csv]
alertcheck diff RUN_ID_A RUN_ID_B
alertcheck questionnaire init|show
alertcheck db update                # 脆弱性 DB・Nuclei テンプレートの更新
alertcheck serve                    # 第 2 段階
```

終了コード: `0` = critical/high なし、`1` = high あり、`2` = critical あり、`3` = 実行エラー。CI での利用を想定する。

## 7. 非機能要件

| 区分 | 要件 |
|---|---|
| 実行環境 | Docker Engine 24 以降、`docker compose` v2。CPU 2 コア・メモリ 4 GB で動作 |
| 実行時間 | Web アプリ 1 件（ポート検査 + HTTP 検査 + ログ 3 か月分 100 万行）で 15 分以内 |
| 負荷 | 既定 5 req/s / ホスト。対象サービスの可用性に影響を与えない |
| 安全性 | 既定は非破壊。アクティブ検査は明示指定と試験用アカウントがある場合のみ |
| 機密性 | 入出力はホストのマウントディレクトリ内に限定。クラウド認証情報は環境変数で受け取り、ファイルやレポートに書き出さない |
| オフライン | `--offline` 時は外部通信をしない（脆弱性 DB は事前取得分を使用） |
| 再現性 | 実行ごとに設定・ツールバージョン・DB 更新日時を記録し、同じ入力で同じ判定になる |
| 拡張性 | 検査はプラグインとして追加でき、IPA 項目との対応は宣言的に定義する |
| 言語 | UI・レポートは日本語。検査 ID・JSON キーは英語 |

## 8. スコープ外

- 認証後画面のクローリングと、SQL インジェクション・XSS 等の網羅的な動的診断（商用 DAST・手動診断の領域）
- 侵入テスト、エクスプロイトの実行
- 常時監視・SIEM 機能（本ツールはスポット点検用）
- 行データの中身を読む個人情報スキャン
- 第三者資産の診断
